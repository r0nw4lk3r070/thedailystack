Security 31 March 2026
The Easy Target

The LiteLLM supply chain attack was three days long, stole real credentials, and hit developers who thought they were doing everything right. It exposed a problem local AI builders share with everyone else: the packages we trust.

What Happened

On 28 March 2026, a threat actor compromised a PyPI maintainer account for LiteLLM — one of the most widely used Python libraries for routing requests across LLM providers. Within hours, two malicious versions were live: 1.82.7 and 1.82.8. They looked identical to the legitimate package. They installed without errors. They ran without warning.

For three days, any developer who ran pip install litellm — or whose CI pipeline did — received malware alongside the library. The payload exfiltrated SSH keys, cloud provider tokens, and Kubernetes secrets to an external server. Not slowly. Immediately.

The malicious versions were taken down on 31 March after discovery by the security community. LiteLLM patched and republished. By then, the window had been open for 72 hours across a global developer base.

The Easy Target

The name LiteLLM might suggest a niche tool. It is not. It sits at the centre of the open-source AI development stack. Developers use it to abstract over OpenAI, Anthropic, Mistral, Ollama, and dozens of other providers. If you are building any kind of AI application in Python, you have probably encountered it. If you are in a team, someone has likely installed it this week.

You don’t have to attack the LLM. You attack the pipe it runs through.

This is what makes supply chain attacks against AI tooling so effective. The attacker doesn’t need to compromise the model, the API, or the infrastructure. They just need to be in the path between the developer and the package they depend on. PyPI, npm, and similar registries are that path — and their account security is only as strong as the weakest maintainer’s password.

For local AI builders, the irony is sharp. The whole premise of local AI is removing dependency on external services — keeping data, compute, and inference inside the perimeter. The LiteLLM attack didn’t penetrate that perimeter. It found the developer building it, before they even reached the perimeter. The exfiltrated SSH keys and Kubernetes secrets don’t reveal what’s in your local model. They reveal the infrastructure around it.

// The credentials that were taken

SSH private keys  —  used for server access and Git authentication

Cloud provider tokens  —  AWS, GCP, Azure access keys

Kubernetes secrets  —  cluster credentials, service account tokens

Environment variables  —  anything in .env files loaded at runtime

None of these are AI-specific. All of them are what you need to destroy or take over a development environment. And all of them are present on the machine of anyone actively building with LiteLLM.

What To Do

The immediate response is straightforward: if you installed LiteLLM between 28 and 31 March 2026, assume compromise. Rotate your SSH keys. Revoke and rotate cloud tokens. Audit Kubernetes secrets. Check your pip install history and your CI logs.

The structural response is harder but more important: pin your dependencies. A requirements.txt with exact version hashes does not protect you from a compromised version that was already published — but it protects you from automatic upgrades pulling in whatever is newest. The LiteLLM attack succeeded partly because developers were running latest.

For teams building on open-source AI tooling, this is also a good moment to ask: which packages in your stack have maintainers with access to millions of developer machines? LiteLLM is one. There are dozens of others in the AI ecosystem with the same exposure profile and the same account security model. This will happen again.
